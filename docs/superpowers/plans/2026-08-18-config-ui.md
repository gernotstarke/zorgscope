# Configuration UI Implementation Plan

**Goal:** A page behind the header's cog where the watched GitHub repositories can be added,
removed and checked, without a redeploy — and where a repository name that GitHub does not
recognise is refused at the moment it is typed rather than discovered weeks later as an empty
tile.

**Status:** plan only. Nothing below is implemented.

**Spec:** [the v1 design](../specs/2026-08-17-zorgscope-reset-design.md) ·
**Requirements:** [functional](../../requirements/04-functional-requirements.md),
[quality](../../requirements/05-quality-requirements.md)

---

## Why this is not a small change

The obvious implementation — a form that writes `config/zorgscope.yaml` — cannot work, and it is
worth being explicit about why before any of it is built.

`config/zorgscope.yaml` is **baked into the image**. `deploy/Dockerfile` copies it in, and
`CONFIG_PATH` points at the copy. The Machine's filesystem is ephemeral and the Machine
[scales to zero](../../decisions/0003-fly-scale-to-zero-external-cron.md): a file written at 14:00
is gone the moment the Machine stops, which on an idle dashboard is minutes later. A write that
survives has to go somewhere durable, and there is exactly one durable place in this
architecture — [Turso](../../decisions/0004-turso-libsql.md).

So the shape of the change is not "a form" but "a second source of configuration, and a rule for
which one wins".

## The decisions this plan makes

**D1 — Editable configuration lives in the database.** A `settings` table, one row per key. The
YAML file keeps everything that is a deployment decision rather than a preference: the timezone,
the refresh interval that has to match cron-job.org, the stale threshold.

**D2 — The file seeds, the database wins.** On start-up, a key with no row in `settings` is seeded
from the file; a key that has a row ignores the file entirely. The alternative — file wins — means
every redeploy silently reverts whatever was configured through the UI, which is the failure that
makes people stop trusting a settings page. This rule needs to be stated on the page itself, next
to the repository list, because it is surprising: after the first edit, changing the YAML does
nothing.

**D3 — Secrets never appear.** The page never renders a credential and never accepts one. It may
say *whether* GitHub has a token, exactly as `make check-env` does — presence, never value
(QS‑4.3). Rotating a token stays `make fly ARGS="secrets set …"`. A settings page that also took
secrets would put `GITHUB_TOKEN` into a POST body, into a form field's value attribute on the next
render, and into any error the page produced.

**D4 — An edit takes effect at the next refresh, not the next restart.** Today `cmd/zorgscope`
builds the fetchers once, at start-up, from `config.Config`. A Machine that has been up for six
hours would keep fetching the old list. The refresh runner must ask for the current repository
list at the start of each run instead.

**D5 — A repository is verified before it is saved.** One GraphQL probe per added repository,
using the configured token, answering "does this exist and can I read it?". This is the feature
that pays for the whole page: the list contained `arc42/quality.arc42.org` for weeks, which is not
a repository — the tile reported a failing source and nobody read the message. The probe runs on
save, outside the refresh path, so it does not touch QS‑3.5's twenty-query budget, which is
counted per refresh run.

**D6 — Removing a repository throws its items away, and re-adding it marks them all NEW.** This
follows from two rules that are working as designed and must not be changed:
`Store.ReplaceItems` deletes rows absent from the incoming set, and `first_seen_at` is written on
INSERT and never updated ([ADR‑0006](../../decisions/0006-first-seen-versus-last-visit.md)). So a
repository removed on Monday and restored on Tuesday arrives with every issue looking new. The
plan does not fix this — it makes the removal form say it, in one sentence, before the button.

## Scope

**In:** the GitHub repository list — add, remove, reorder-free, verified on save; the cog wired to
the page; the precedence rule visible on it.

**Out, deliberately, for a later increment:** Plausible sites and the Todoist filter (same
mechanism, no new problems, and the repository list is the one that is actually wrong today); the
refresh interval and stale threshold (they have to agree with cron-job.org, so editing them in one
place invites drift); anything to do with secrets (D3).

## Global constraints

These bind every task and are the same ones the v1 plan sets out:

- `internal/domain` imports only the standard library (QS‑5.1); `depguard` enforces it.
- No secret value may be logged, rendered or written to the repository (QS‑4.3).
- Every route is declared in `routes()` with the credential it needs (QS‑4.1). The configuration
  routes are `authSessionPage` for the page and `authSessionFragment` for the forms — never
  public, unlike `POST /theme`, because these ones change what the system does.
- Times are RFC 3339 UTC strings in SQL.
- Every task ends with `make check` green.
- No sixth external dependency without a decision record.

## CSRF

The session cookie is `SameSite=Lax`, which a browser does not send on a cross-site POST, and the
CSP names `form-action 'self'`. Together those cover the forms below without a token, and the
reasoning belongs in a comment on the handler rather than in someone's head — the day the cookie's
SameSite attribute is relaxed for an unrelated reason, these forms become forgeable.

## Task 1: The settings table and its store methods

**Files:** `internal/adapters/libsql/migrations/0003_settings.sql`,
`internal/adapters/libsql/store.go`, `internal/ports/ports.go`

```sql
CREATE TABLE IF NOT EXISTS settings (
  key        TEXT PRIMARY KEY,
  value      TEXT NOT NULL,   -- JSON, so a list is one row rather than an ordered table
  updated_at TEXT NOT NULL
);
```

```go
// ports.Store gains:
Setting(ctx context.Context, key string) (value string, ok bool, err error)
SetSetting(ctx context.Context, key, value string, now time.Time) error
```

`ok` distinguishes "no row" from "a row holding the empty string", which is exactly the
distinction D2 turns on: an empty repository list configured on purpose must not be re-seeded from
the file on the next start.

**Acceptance:** a value survives a round trip; a missing key reports `ok == false`; setting an
existing key overwrites it and moves `updated_at`; the migration is idempotent across two
`make db-migrate` runs.

## Task 2: The settings service and the precedence rule

**Files:** `internal/settings/settings.go`, `internal/settings/settings_test.go`

```go
// Settings resolves the effective configuration: the file as the seed, the database as the
// authority (D2).
type Settings struct { /* store, file config, clock */ }

func New(store ports.Store, file config.Config, clock ports.Clock) *Settings
func (s *Settings) Repos(ctx context.Context) ([]string, error)
func (s *Settings) SetRepos(ctx context.Context, repos []string) error
func (s *Settings) Seed(ctx context.Context) error   // called once at start-up
```

`Repos` reads the database on every call. It is one indexed lookup by primary key against a
database this process is already talking to, and caching it would need an invalidation path
between the web handler that writes and the runner that reads.

**Acceptance:** with no row, `Repos` returns the file's list and `Seed` writes it; with a row, the
file is ignored even when it differs; `Seed` run twice changes nothing; an empty list stored on
purpose stays empty across a restart.

## Task 3: The runner reads the current list

**Files:** `cmd/zorgscope/main.go`, `internal/refresh/runner.go`,
`internal/adapters/github/issues.go`

The GitHub fetchers take their repository list from `Settings` at the start of each run rather
than from a slice captured at start-up (D4). The smallest change that achieves it is a provider
function on `github.Config`:

```go
type Config struct {
    Token, BaseURL string
    Repos          func(ctx context.Context) ([]string, error)
}
```

**Acceptance:** a fetcher built before the list changed fetches the new list on its next run; a
provider that errors fails the source without failing the whole run; the cost test still shows two
GraphQL queries per repository.

## Task 4: The configuration page

**Files:** `internal/web/config.go`, `internal/web/templates/config.html`,
`internal/web/server.go`, `internal/web/templates/layout.html`,
`internal/web/static/app.css`

`GET /config`, `authSessionPage`. Lists the repositories with, for each, the source state the
dashboard already holds: when it last succeeded, and its error if it is failing. That is the
diagnosis the list itself cannot give — a name that is wrong and a token that lacks access look
identical until the error is beside them.

Below the list: whether each source has a credential (presence only, D3), the two-of-ten
repository budget in words, and one sentence on the precedence rule from D2.

The cog in `layout.html` stops being disabled and becomes a link to `/config`; the
`settings-button` markup and the test asserting it is inert both go.

**Acceptance:** anonymous `GET /config` redirects to `/login`; the page names every configured
repository and no credential value; the canary test that sweeps every route for secrets still
passes.

## Task 5: Adding and removing a repository

**Files:** `internal/web/config.go`, `internal/web/config_test.go`,
`internal/web/templates/config.html`

`POST /config/repos/add` and `POST /config/repos/remove`, both `authSessionFragment`, both
redirecting back to `/config` on success.

The add field accepts what a person actually has in the clipboard — all of these normalise to
`arc42/faq.arc42.org-site`:

| Pasted | Accepted |
|--------|----------|
| `arc42/faq.arc42.org-site` | as is |
| `https://github.com/arc42/faq.arc42.org-site` | yes |
| `https://github.com/arc42/faq.arc42.org-site/issues` | yes, path beyond the repository ignored |
| `git@github.com:arc42/faq.arc42.org-site.git` | yes |
| `https://gitlab.com/x/y` | refused, named as not a GitHub URL |

Rejections are refusals with a reason, never silent normalisation into something else.

Validation before the probe: `owner/name` shape, no duplicate, and the ten-repository cap from
QS‑3.5 — the eleventh entry is refused with the budget stated, because the alternative is a
refresh that quietly exceeds its query budget.

The remove form carries D6's sentence: removing a repository deletes its stored issues, and adding
it back later shows all of them as new.

**Acceptance:** each row of the table above; the eleventh repository is refused; a duplicate is
refused; a removal takes effect on the next dashboard load; a form posted without a session is
401.

## Task 6: Verifying a repository against GitHub

**Files:** `internal/adapters/github/probe.go`, `internal/web/config.go`

```go
// Probe reports whether owner/name exists and is readable with the configured token.
func (f *IssueFetcher) Probe(ctx context.Context, repo string) error
```

One `repository(owner:, name:) { id }` query. Three outcomes worth telling apart, because they
have three different fixes:

- **not found** — the name is wrong, or the repository is private and the token cannot see it
- **no token configured** — the entry is saved unverified, with a note; a dashboard being set up
  before its secrets are in place must not be unable to configure itself
- **the probe itself failed** (network, 5xx) — saved unverified, with the reason; GitHub being
  down is not a reason to refuse a correct name

**Acceptance:** a good name saves and reports verified; a misspelling is refused with the name
quoted; a probe timeout saves with a note rather than refusing; the probe is bounded by a context
timeout well under the refresh ceiling.

## Task 7: Documentation

**Files:** `docs/decisions/0009-configuration-in-the-database.md`,
`docs/concepts/configuration.md`, `docs/requirements/04-functional-requirements.md`

An ADR for D1 and D2 — where editable configuration lives and which source wins — since it is the
decision a future reader will otherwise have to reverse-engineer from a precedence check. A
requirement for the page itself, so the feature is not the only thing on the dashboard with no id.
A paragraph in the concepts page saying that after the first edit the YAML no longer decides the
repository list.

## What this leaves open

- **A second machine.** Nothing here is safe against two Machines writing settings at once. Today
  there is one, and `min_machines_running = 0` keeps it that way; if that changes, the write path
  needs the same lease treatment the refresh already has.
- **No history.** An edit overwrites. Whether "who changed the list, and when" is worth a table is
  a question for the day it is missed — the `updated_at` column is there so at least "when" can
  be answered.
- **Ordering.** The list is displayed in the order it is stored. Configuration order is what the
  sites tile relies on (FR‑3.1 AC3); the repository list has no equivalent, so reordering is not
  offered until something needs it.

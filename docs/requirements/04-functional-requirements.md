# 4. Functional requirements

Epics (E‑x) with user stories (FR‑x) and acceptance criteria (AC) a test can check.
Priority: **M** must (v1), **S** should (v2), **W** won't.

"The user" is always Gernot (S‑1). Terms in *italics* are defined in the [glossary](06-glossary.md).

The requirements below were renumbered in the 2026-09-15 stateless reset: everything that assumed
a database — build status, refresh runs, Slack notifications, the in-app documentation pages, the
stop control, htmx polling — was retired, and the ids of the stories that described it are not
reused. See [ADR‑0010](../decisions/0010-stateless-no-database.md) for why, and the design's own
"out of scope, deliberately" (`docs/superpowers/specs/2026-09-15-stateless-reset-design.md`, §12)
for what would have to change to bring any of it back.

## E‑1 The dashboard

| Id | Prio | Story | Acceptance criteria |
|----|------|-------|---------------------|
| FR‑1.1 | M | As the user I open one page and see everything at once, so that a glance is enough. | AC1 The dashboard lists the open issues and pull requests of the configured repositories, one section per repository that currently holds at least one item, in configuration order; a repository no longer configured but still holding items from an earlier snapshot appears after the configured ones. AC2 The list is read from an in-memory snapshot at most `github.cache_ttl` old; two page views inside that window share one fetch rather than each fetching on its own. AC3 Each item shows its title, number, URL, author, kind and the age of its creation and last update. AC4 The header states when the snapshot's items were fetched, or "never" before the first fetch has returned anything. |
| FR‑1.3 | M | As the user I can fetch immediately rather than wait for the cache to go stale. | AC1 "Refresh" (`POST /refresh`) invalidates the cached list and redirects to the page, which then fetches instead of serving the cache. AC2 The action is a plain form behind the session, so it works without JavaScript and is refused to an anonymous visitor. |
| FR‑1.4 | M | As the user I notice when the data is stale or GitHub is failing, without losing what I already had. | AC1 A failed fetch keeps the previous items; the list is never blanked by an upstream failure. AC2 A first fetch that fails — before anything has ever been fetched — yields an empty list with the notice rather than an error page. AC3 The notice states since when GitHub has been failing and, once there is one, when the list being shown was last fetched; the upstream error text is scrubbed of every configured secret before it is shown. AC4 A repository that fails on its own does not blank the others: the repositories that did fetch are shown current, alongside the notice for the one that did not, and the one that did not keeps its previous items; such a partial fetch does not advance the list's fetched-at time (unless nothing had been fetched before). |
| FR‑1.5 | M | As the user I want the page to work in light and dark appearance. | AC1 The page follows the operating-system appearance by default; a control cycles system → light → dark → system and is remembered in a cookie for a year. AC2 The control returns the visitor to the local path it was pressed on; an absolute URL, a protocol-relative URL, or any other value that is not an ordinary local path falls back to the dashboard rather than being followed, so the control cannot be turned into an open redirect. |
| FR‑1.8 | M | As the user I see each site's open pull requests and issues at a glance. | AC1 `/sites` shows one tile per site configured in `github.sites`, in configuration order, preceded by the Security tile (FR‑1.13 AC6) and — when some watched repository is claimed by no site — followed by a last tile called Other holding those repositories; a site with nothing open keeps its tile. AC2 A tile lists at most three pull requests and four issues, most recently updated first; its totals are taken before that cut. AC3 When a tile has cut something, it links to the list filtered to its repository — on Other, one link per repository. AC4 Both views carry the top bar's List \| Sites \| Radar \| Contributors switch marking the view being shown, and Refresh returns to the view it was pressed on. AC5 Each tile carries its site's colour from the arc42 brand registry, text on and inside a tile keeps a contrast of at least 4.5:1 in both appearances, and colour is never the only way a site is told apart. |
| FR‑1.9 | M | As the user I see that GitHub is being asked, and the page arrives on its own. | AC1 While a fetch is running **and the snapshot holds no items**, `GET /`, `GET /sites`, `GET /radar`, `GET /contributors` and `GET /search` show the wait page — the mark, animated, with a status line naming how many repositories are being asked — and not a list, filters or tiles. While a fetch is running and the snapshot holds items, each shows its ordinary page, drawn from that snapshot (ADR‑0013). AC2 The page arrives without any action. From the wait page: the page the visitor asked for, with its query, replaces it — with JavaScript by polling every 500 ms and swapping the page in once the fetch has ended, without it by reloading every two seconds. From a stale page: the list polls `GET /items` every 500 ms from an element inside the fragment, which the arriving fragment removes. AC3 A fetch that fails ends the waiting the same way, with the page's error notice and the previous or empty list. AC4 With reduced motion requested the mark neither rotates nor scales, and the status line is shown regardless; colour is never the only signal. AC5 During a fetch an htmx request other than the poll that asks for a fragment — the filter form — is answered from the current list, never with the wait page; the top-bar search, which replaces the whole page body, is answered with the wait page like a navigation, and the poll it arrives with swaps the results in. AC6 A stale list states the time its items were fetched at and that a fetch is running; the status line is announced politely and colour is never the only signal. AC7 On the wait page a stored copy of the visitor's last list may be shown as a labelled placeholder; it is replaced by the arriving page, it is refused when its epoch does not match the document's or when it is older than seven days, and its absence leaves the wait page exactly as it is without it. |
| FR‑1.10 | M | As the user I see the family's colours and each item's labels on the list, and I see what has gone quiet. | AC1 Every page carries the arc42 rainbow band under the top bar, the same in both appearances. AC2 Each repository group on the list carries a stripe in its site's colour, slate for a repository no site claims; the repository name stays in the page's text colour; every stripe keeps 3:1 against the page in both appearances. AC3 An item's labels are shown as chips after its title, in GitHub's order; bug, enhancement, documentation, question, help wanted and in progress — matched case-insensitively, spaces and hyphens alike — each have a fixed colour, any other label is a neutral chip; chip text keeps 4.5:1 against the chip in both appearances; a colour never reaches the page except as a class. AC4 An item not updated for 90 days is quiet: its title is dimmed and its meta line says "quiet"; the order of the list does not change. |
| FR‑1.11 | M | As the user I reach every view and action from the top bar. | AC1 The top bar of every signed-in page carries, above the rainbow band, the List \| Sites \| Radar \| Contributors switch marking the current view, the search box, Refresh and Log out; the sign-in page carries only the brand and the appearance control. AC2 The page body keeps the fetched time and the error notice above its content. AC3 Refresh returns to the page it was pressed on, query included, through the same validation as before. |
| FR‑1.12 | S | As the user I set how the dashboard greets me, and it remembers. | AC1 A control in the top bar opens a panel holding the landing view, the quiet threshold, the browser‑list setting and the appearance; it opens, changes and closes with no JavaScript. AC2 Each setting is stored in a cookie of its own for a year; an absent or unrecognised value is the default — list, 90 days, on — and no value read from a cookie is ever rendered as text. AC3 The landing view decides where GET / goes, and asking GitHub starts no later than it does without the setting. AC4 The quiet threshold decides which items are marked quiet (FR‑1.10 AC4); "never" marks none. AC5 Turning the browser‑list setting off removes what that browser has stored (FR‑1.9 AC7). |
| FR‑1.13 | S | As the user I cannot miss a security item or a dependency update. | AC1 An item citing a CVE or GHSA identifier in its title or body, or labelled security in any case, is marked Security; otherwise an item authored by Dependabot or Renovate, or labelled dependencies in any case, is marked Dependency; nothing else is marked. AC2 A marked item carries a solid chip — "Security" in red with a shield, "Dependency" in amber — on the list, the search results and the Sites tiles alike, and 12 px of diagonal hazard tape in the same colour down its left edge on the list and the search results; the Security tile's heading is red hazard tape while it holds a marked item (FR‑1.13 AC6); the chip's title names the evidence; the label that produced the mark (`security`, `dependencies`) is not drawn a second time as a label chip; colour is never the only signal. AC3 A Security item is never marked quiet (FR‑1.10 AC4). AC4 The list states how many Security items are open, over every open item whatever the filter, and says nothing when there are none. AC5 No request beyond those already made is sent to GitHub (QS‑3.5). AC6 `/sites` opens with a Security tile, before every site tile, holding every marked item wherever it is open — at most three pull requests and four issues, Security before Dependency and only then most recently updated first, each row naming its repository. It states its totals before the cut as "N security · N dependency", says "All clear — no security or dependency items open." when nothing is marked, and links to the list narrowed to everything it marks only when it cut something. Its heading is red hazard tape while, and only while, it holds a marked item — on an ordinary day it is a neutral band and the tile is no taller than its one line — and it carries a rule down its edge while, and only while, a Security item is open; the word Security in its heading is there either way. AC7 The list can be narrowed to a tier: `tier=security` shows the Security items, `tier=dependency` shows those and the Dependency ones, since a bump that fixes a vulnerability is still a bump. It is a control of the filter form, works without JavaScript, and is carried in the URL like every other filter. The security count of AC4 links to `?tier=security`. |
| FR‑1.14 | S | As the user I see first what needs me. | AC1 An item needs the owner — the one GitHub login `github.owner` names — for the loudest of these reasons: it is marked Security or Dependency (FR‑1.13), whoever opened it; it is a pull request asking the owner for a review; it is a pull request opened by someone other than the owner, draft or ready (Contribution); it is a pull request the owner opened, not yet merged (Your PR). Every open pull request therefore needs the owner until it goes stale (AC10); nothing else does. Without `github.owner` every pull request is a Contribution. AC2 The unfiltered list opens with a "Needs you" band — first under the top bar, above the fetched line, the filter and the repository groups — holding every such item once, Security, Dependency, Review requested, Contribution and Your PR in that order and most recently updated first within each, and stating how many there are. AC3 Each row is one line — the reason as a word (the tier chip for a marked item), PR or Issue, number, title, author, repository with its site's colour, and when it was last updated; colour is never the only signal. Every item of the band is also in the list below, where it is drawn at full weight and every other item a step quieter; nothing leaves the list (QG‑1). AC4 A filter narrows the list, not the band: the band counts every open item whatever the filter, and stays where it is while the filter changes. AC5 When nothing needs the owner the band says "Nothing right now."; when nothing is open at all there is no band. AC6 The band shows at most ten rows; the rest are behind a disclosure that opens without JavaScript. AC7 Review requests are read as a field of the pull request query already made: no request is added (QS‑3.5). AC8 A marked row of the band carries the hazard tape of FR‑1.13 AC2, and while a Security item is in it the whole band is framed in red. AC9 Every signed-in page's top bar leads with how many items need the owner — "N need you", or "Nothing needs you" — linking to the band, ahead of the open totals. AC10 An item with no activity for more than six months no longer needs the owner now, unless it is a Security item: it leaves the top of the band, the band's count, the top bar's count and the list's full weight, and is listed behind a disclosure "N older than 6 months" at the end of the band, which opens without JavaScript. An item whose update time is unknown is never stale. |
| FR‑1.15 | S | As the user I see at a glance, as a picture, where things are moving and what is loud. | AC1 `GET /radar` draws every open item of the snapshot as a blip on a radar scope, as inline SVG with no JavaScript; nothing the list shows is missing (QG‑1). AC2 A blip's bearing is the sector of the site claiming its repository — one equal sector per configured site in configuration order, then Other for every repository no site claims, including one left over from an earlier configuration — and its place inside the sector is the same on every render; its distance from the centre grows with the time since its last update on a logarithmic scale up to two years at the rim, where an item with an unknown update time also stands; range rings are labelled 1 d, 1 wk, 1 mo, 6 mo and 1 yr; each sector carries its site's colour on the rim and as two faint dotted lines inside its edges. AC3 An issue is a circle and a pull request a diamond, filled in its site's colour; a Security item (FR‑1.13) is larger, ringed in red hazard tape, pulses and is tagged "⚠ #n"; a Dependency item is ringed in amber hazard tape; a pull request that needs the owner now (FR‑1.14) is ringed in the accent colour and tagged "#n"; only Security pulses; marked items never fade, others fade with idle time; the loudest are drawn on top; colour is never the only signal. AC4 Every blip is a link that opens its item on GitHub in a new tab; hovering it or reaching it with the keyboard shows its data block — kind, repository, number, title, why it is marked, author, opened, last activity, labels and the start of its summary — in a panel beside the scope, in a fixed layout whose keys are drawn once; the block is the link's accessible name. The scope takes the width of the window, not of the page's reading column, and never more than its height. Without a blip hovered the panel holds the legend and the counts. AC5 A sweep turns once every eight seconds and each blip flashes as it passes; with reduced motion requested nothing moves. AC6 No style attribute is rendered (QS‑4.4); the page stays within QS‑2.3's budget over the representative fixture. AC7 Radar can be chosen as the landing view (FR‑1.12). |

FR‑1.2 (`NEW` and the seen mark) was retired on 2026-09-18, see [ADR‑0012](../decisions/0012-no-seen-mark.md); the id is not reused.

## E‑2 Filters

| Id | Prio | Story | Acceptance criteria |
|----|------|-------|---------------------|
| FR‑2.1 | M | As the user I narrow the list by repository, kind, creation date and text. | AC1 The list can be narrowed by repository, by kind (issue or pull request), by items created since a date, and by a case-insensitive text search over title and summary; every axis is optional and the axes combine. The text axis has no box of its own — the top bar's search is the one place to type (FR‑12.1) — but a `q` in the URL narrows the list and survives a change to any other control. AC2 The filter is carried in the URL's query string, works as a plain GET form without JavaScript, and the htmx fragment the same form also drives (`GET /items`) renders identically to the page's own list. Its controls sit behind one disclosure that states how many axes are in force and is open whenever one is; a narrowed list offers "Clear filter" beside its count. AC3 The filter never changes a repository's total. AC4 A date is read in the configured timezone rather than UTC, so "since today" means the visitor's own day. |

## E‑8 Configuration and access

| Id | Prio | Story | Acceptance criteria |
|----|------|-------|---------------------|
| FR‑8.1 | M | As the operator I configure what is watched in one YAML file and supply every secret through the environment. | AC1 `config/zorgscope.yaml` lists the timezone, the repositories to watch, the repository whose push access admits a visitor, and how long a fetched list may be reused before a page view refetches it; it contains no secret value. AC2 `GITHUB_OAUTH_CLIENT_ID`, `GITHUB_OAUTH_CLIENT_SECRET` and `GITHUB_TOKEN` come from the environment (Fly secrets in production); the process refuses to start without any one of them, naming which is missing. AC3 An invalid file — an unknown field, an empty repository list, a malformed `cache_ttl`, a repository not in `owner/name` form — aborts start-up with a message naming the offending field, never a value. AC4 No secret value is ever logged, returned in a response, or otherwise rendered. AC5 `github.sites` is optional; a site with an empty or duplicate name, an address that is not an absolute `https` URL, a repository not in `owner/name` form, not listed in `github.repos` or claimed by a second site, a colour outside the fixed palette, or a tag longer than three characters aborts start-up with a message naming the offending field.  Per‑visitor preferences (FR‑1.12) are held in cookies and name nothing the deployment depends on. |
| FR‑8.3 | M | As the user I sign in with my GitHub account, once per browser, and only a collaborator with push access is admitted. | AC1 An unauthenticated browser request to the dashboard is redirected to a sign-in page, not answered with a bare 401; a non-navigation request (an htmx fragment or a form action) is refused with 401 instead, since redirecting it would paint the sign-in page into a tile. AC2 Signing in with GitHub through the registered OAuth App, with no scopes requested, issues a signed, HttpOnly, SameSite=Lax session cookie whose payload is an expiry and nothing else; the visitor's GitHub token is used for one permission check and never stored. AC3 Only a GitHub user with push or admin permission on the configured `auth_repo` is admitted; anyone else is refused with a page that says so and receives no session. AC4 The cookie's signing key derives from the OAuth client secret, so rotating the secret invalidates every session immediately. AC5 Refused sign-in callbacks are rate-limited by an in-memory bucket keyed by client IP, and are logged with the reason but never the authorization code, the state or the visitor's token. |

## E‑12 Search and people

Finding one open item among a few hundred, and seeing the people who opened them, from the top bar of any page.

| Id | Prio | Story | Acceptance criteria |
|----|------|-------|---------------------|
| FR‑12.1 | M | As the user I find an item by a word from its title, its contributor, a label or its repository, from any page, in seconds. | AC1 `GET /search?q=` ranks the snapshot: every word must match; a word matches case-insensitively as a substring of the title, the author login, a label, the repository name or the summary; `issue`, `issues`, `pr`, `prs` and `pull` are reserved and narrow the kind; scores are title at a word start 4, title elsewhere 2, contributor 3, label 3, repository 1, summary 1, summed; ties break by last update. AC2 The results page shows the count, and per hit the kind, repository, number, title with the matched text marked, labels, author, last update and which fields matched; an empty query shows a hint; nothing is reflected unescaped. AC3 The box in the top bar fetches results as the user types, 300 ms after the last keystroke, and pushes the results URL; Enter and JavaScript-off reach the same page; Cmd‑K or Ctrl‑K focuses the box, Escape leaves it. AC4 During a fetch the page behaves as FR‑1.9 prescribes: a navigation waits, and so does a search typed in the top bar, since its form replaces the whole page body — the wait page arrives with a poll for the results URL and swaps the results in when the fetch ends. |
| FR‑12.2 | M | As the user I see who opened the open issues and pull requests. | AC1 `GET /contributors` lists one row per author with login linking to their GitHub profile, open pull requests, open issues, the repositories in configuration order, last activity, and a link to the search for their login; ordered by open items, then last activity, then login; an author GitHub no longer knows is listed last as "unknown" and links nowhere. AC2 The page carries the switch marking it and the shared header. |

## Explicitly out of scope

Build status per repository, Slack notifications, item-level dismissals, history of any kind,
background refresh, a runtime configuration page, and everything else a database would be needed
for — see [ADR‑0010](../decisions/0010-stateless-no-database.md). News and RSS feeds, "unanswered"
detection, daily snapshots, credential and TLS expiry watching, passkey authentication, a native or
Wails client, and a write-capable public JSON API were already out of scope before the stateless
reset. Site statistics (Plausible) and task lists (Todoist) were removed 2026-09-14 after a month of
not being looked at. Closed items are out of scope, and so is `NEW` with its seen mark, retired 2026-09-18 ([ADR‑0012](../decisions/0012-no-seen-mark.md)).
